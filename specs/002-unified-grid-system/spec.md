# Feature Specification: 统一网格系统 — 浮动文件夹窗口与全域拖拽

**Feature Branch**: `002-unified-grid-system`

**Created**: 2026-05-22

**Updated**: 2026-05-22

**Status**: Draft

**Input**: User description: "重新设计前端网格系统，使文件夹成为网格中的普通容器。文件夹以浮动窗口方式展开（非原地放大），窗口内元素可像主面板一样拖动。拖出窗口边框松手即移至主面板并自动排列。展示模式（list/1x1网格）同时影响折叠态和展开态。文件夹有统一最大尺寸，超出加滚动条。"

## 问题分析

### 当前架构的根本限制

当前实现存在以下结构性问题，导致多轮 bug 修复后仍无法达到期望行为：

1. **文件夹弹窗使用 `createPortal` 脱离 DndContext DOM 树**：弹窗内的拖拽无法与主面板的 dnd-kit 共享状态，需要用 Pointer Events 单独实现一套拖拽逻辑，导致行为不一致。
2. **弹窗内条目与主面板条目使用不同的组件渲染**：外观和交互行为存在差异，无法保证一致性。
3. **布局持久化时机错误**：仅拖拽结束时保存 gridX/gridY，其他操作（合并创建文件夹、改大小）用旧的 DB 值覆盖，导致条目跳到第一行。
4. **合并创建文件夹先创建再移动**：用户看到新文件夹先出现在第一行，然后跳到目标位置。

### 理想模型

- 网格上每个单元格就是一个可交互的容器
- 文件夹是一个包含多个子单元格的容器，折叠时按当前展示模式显示子项预览
- 点击文件夹时打开浮动窗口（出现在文件夹卡片附近，覆盖在桌面上方），窗口内子项使用与主面板一致的网格布局和拖拽系统
- 浮动窗口打开期间，主面板完全阻塞（不可交互），用户必须关闭浮动窗口才能操作主面板
- 网页条目在任何位置（主面板、文件夹折叠态、文件夹浮动窗口内）具有完全一致的外观和交互行为
- 将条目拖出文件夹窗口边框并松手即移至主面板，自动排列到第一个空位
- 文件夹展示模式（list/网格）同时影响折叠态和浮动窗口；list 折叠态不截断条目，全部可滚动显示，右下角预留交互区域用于打开文件夹

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 统一网格组件系统 (Priority: P1)

所有主面板元素（网页条目和文件夹）使用统一的网格组件系统。每个组件占据 m×n 个网格单元格，具有一致的大小设置和排列方式。网页条目在任何位置的外观和交互行为完全一致——对于用户来说，它们就是同一个东西放在不同的地方。

**Why this priority**: 这是整个系统的基石。如果组件不能在任何位置表现一致，其他所有功能都无法正确实现。

**Independent Test**: 在主面板创建一个 1×1 网页条目和一个 2×2 文件夹（含 4 个网页条目），验证：条目在主面板和文件夹内使用相同组件渲染，外观一致，点击/右键/拖拽行为一致。

**Acceptance Scenarios**:

1. **Given** 主面板上有一个 1×1 网页条目，**When** 用户查看其外观，**Then** 条目显示为带有图标和名称的标准卡片。
2. **Given** 一个 2×2 文件夹内有一个网页条目，**When** 文件夹浮动窗口打开后用户查看该条目，**Then** 该条目外观与主面板上的 1×1 条目完全一致。
3. **Given** 任意位置的网页条目，**When** 用户右键点击，**Then** 弹出完全一致的上下文菜单。
4. **Given** 主面板上有不同大小的组件（1×1、1×2、2×2、3×2），**When** 用户查看网格排列，**Then** 所有组件按 m×n 网格整齐排列，无溢出或重叠。

---

### User Story 2 - 文件夹浮动窗口 (Priority: P1)

用户点击文件夹时，打开一个浮动窗口显示在文件夹卡片附近。窗口不推动任何相邻元素，不可被用户拖动移动。窗口内的子项使用与主面板一致的网格布局和拖拽系统。浮动窗口打开期间，主面板完全阻塞，用户必须关闭浮动窗口才能操作主面板。点击窗口外部区域即关闭窗口。

**Why this priority**: 这是文件夹交互的核心体验，直接决定了用户对文件夹功能的整体感受。

**Independent Test**: 创建一个 2×2 文件夹（含 6 个条目），点击后验证：浮动窗口出现，位置固定，相邻元素不受影响，窗口内条目与主面板条目一致。

**Acceptance Scenarios**:

1. **Given** 一个 2×2 文件夹（含 6 个条目），**When** 用户点击文件夹，**Then** 浮动窗口出现在文件夹卡片附近（遇到面板边界时自动靠拢调整），文件夹折叠态保持不变。
2. **Given** 浮动窗口已打开，**When** 用户查看相邻元素，**Then** 相邻元素位置完全没有变化，未被推动或挤开。
3. **Given** 浮动窗口已打开，**When** 用户查看窗口内的条目，**Then** 条目使用与主面板一致的展示模式（list 或 1×1 网格），外观与主面板条目完全一致。
4. **Given** 文件夹内条目数量未超出文件夹容量上限，**When** 用户尝试点击文件夹，**Then** 文件夹不打开浮动窗口（因为所有条目都已正常显示）。
5. **Given** 浮动窗口已打开，**When** 用户点击窗口外部或按 Esc，**Then** 浮动窗口关闭，主面板恢复可交互状态。
8. **Given** 浮动窗口已打开，**When** 用户尝试操作主面板（拖拽、右键等），**Then** 主面板不响应任何交互（完全阻塞）。
6. **Given** 文件夹展示模式设置为 list，**When** 用户点击文件夹打开浮动窗口，**Then** 窗口内条目以 list 模式排列。
7. **Given** 文件夹展示模式设置为 1×1 网格，**When** 用户点击文件夹打开浮动窗口，**Then** 窗口内条目以 1×1 网格排列，与主面板布局一致。

---

### User Story 3 - 全域统一拖拽 (Priority: P1)

拖拽逻辑在所有位置表现一致：主面板、文件夹折叠态内的条目、文件夹浮动窗口内的条目。浮动窗口打开期间主面板被阻塞，用户可以将条目从浮动窗口内拖到窗口边框外松手移至主面板，或直接拖动文件夹折叠态中的可见条目。主面板上的条目只能通过主面板右键菜单"移动到文件夹"功能移入文件夹。

**Why this priority**: 拖拽是管理导航条目的主要交互方式，不一致的拖拽体验直接影响用户效率。

**Independent Test**: 打开一个文件夹浮动窗口，将其中一个条目拖到窗口外部松手，验证：条目离开文件夹以 1×1 卡片形式出现在主面板上，自动排列到第一个空位。

**Acceptance Scenarios**:

1. **Given** 文件夹浮动窗口已打开，**When** 用户拖拽一个条目到窗口边框外部并松手，**Then** 条目以 1×1 卡片形式自动排列到主面板第一个空位。
2. **Given** 文件夹折叠态中有一个可见的条目（未缩小），**When** 用户拖拽该条目到文件夹外，**Then** 条目从文件夹中移出并自动排列到主面板。
4. **Given** 文件夹折叠态中被缩小的条目，**When** 用户尝试交互，**Then** 这些条目不可点击且不可拖动。
5. **Given** 用户按住 Alt 拖拽一个条目到另一个条目上，**When** 松开鼠标，**Then** 新文件夹在两个条目的原始位置原地生成（不跳到第一行再移动）。

---

### User Story 4 - 网格碰撞与布局行为 (Priority: P2)

当文件夹或组件改变大小时，周围元素的布局行为如下：组件以左上角为锚点原地扩展；如果右侧有其他组件，将那些组件向右推移；如果右侧已是面板边界，则组件自身移到下一行。合并创建文件夹时，新文件夹直接在两个原始条目的位置生成，不会先出现在第一行。

**Why this priority**: 布局行为直接影响用户对操作结果的预期和信任感。

**Independent Test**: 将一个 1×1 文件夹改为 2×2，验证：文件夹左上角不动，右侧的条目被推移。

**Acceptance Scenarios**:

1. **Given** 一个 1×1 文件夹在位置 (3,2)，右侧 (4,2) 有一个条目，**When** 用户将文件夹改为 2×2，**Then** 文件夹左上角保持在 (3,2)，(4,2) 的条目被向右推移。
2. **Given** 一个 1×1 文件夹在面板最右列，**When** 用户将文件夹改为 2×2，**Then** 文件夹移到下一行（因为右侧没有空间）。
3. **Given** 用户 Alt+拖拽条目 A 到条目 B 上，**When** 松开鼠标，**Then** 新文件夹直接在 A 和 B 的原始位置生成，用户看到的动画是 A 和 B 原地合入新文件夹，而不是新文件夹先出现在第一行再跳转。

---

### User Story 5 - 展示模式与文件夹尺寸 (Priority: P2)

文件夹可以设置展示模式（list 或 1×1 网格），该设置同时影响折叠态和展开态的显示。文件夹有一个统一的最大尺寸，不论任何排列方式都共用此最大尺寸。当内容超出最大尺寸时，显示滚动条。

**Why this priority**: 展示模式和尺寸管理是文件夹的基础功能，影响用户的日常使用体验。

**Independent Test**: 创建一个文件夹，设置为 list 模式，验证折叠态和展开态均以 list 显示。添加超过最大尺寸的条目，验证出现滚动条。

**Acceptance Scenarios**:

1. **Given** 一个文件夹展示模式设置为 list，**When** 用户查看文件夹折叠态，**Then** 子项以 list 形式显示，全部可见（不截断），超出文件夹尺寸时可滚动。
2. **Given** 一个文件夹展示模式设置为 list，**When** 用户打开浮动窗口，**Then** 窗口内子项以 list 形式显示。
3. **Given** 一个文件夹展示模式设置为 1×1 网格，**When** 用户查看文件夹折叠态，**Then** 子项以网格形式排列（溢出子项缩小放入最后一个网格，最多 4 个缩小项）。
4. **Given** 一个文件夹展示模式设置为 1×1 网格，**When** 用户打开浮动窗口，**Then** 窗口内子项以 1×1 网格排列。
5. **Given** 文件夹内条目数量超出最大尺寸可容纳的范围，**When** 用户查看浮动窗口，**Then** 窗口内出现滚动条，用户可滚动查看所有条目。
6. **Given** 文件夹最大尺寸为 2×2，**When** 不论展示模式为 list 或网格，**Then** 浮动窗口的最大可视区域大小一致（共用同一最大尺寸）。
7. **Given** 文件夹展示模式为 list 且折叠态中条目可滚动，**When** 用户点击文件夹右下角预留的交互区域，**Then** 浮动窗口打开。

---

### User Story 6 - 文件夹折叠态条目交互 (Priority: P2)

文件夹折叠态中，未被缩小的条目（即正常大小的条目）可以直接点击打开网页，也可以直接拖动。列表模式下显示的条目预览也可以直接点击打开。被缩小到溢出网格中的条目不可点击、不可拖动。

**Why this priority**: 用户期望任何可见的网页条目都可以直接交互，不管它是否在文件夹内。

**Independent Test**: 创建一个 2×2 文件夹（含 3 个条目），在折叠态下点击其中一个条目，验证网页在新标签页打开。

**Acceptance Scenarios**:

1. **Given** 一个 2×2 文件夹（含 3 个条目），**When** 用户在折叠态点击某个条目的图标，**Then** 该条目的网页在新标签页打开。
2. **Given** 文件夹以 list 模式显示，**When** 用户点击列表中的某个条目，**Then** 该条目的网页在新标签页打开。
3. **Given** 一个 2×2 文件夹（含 6 个条目，溢出网格中显示了 4 个缩小条目），**When** 用户尝试点击缩小条目，**Then** 点击事件不触发打开网页（这些条目不可交互）。
4. **Given** 文件夹折叠态中的正常大小条目，**When** 用户右键点击该条目，**Then** 弹出与主面板一致的上下文菜单。

---

### Edge Cases

- 文件夹浮动窗口出现在文件夹卡片附近。如果卡片靠近面板左边界或右边界，窗口自动向内靠拢，不超出面板边界。
- 浮动窗口打开期间，主面板完全阻塞——用户不可拖拽、右键或点击主面板上的任何元素。
- 浮动窗口不可被用户拖动移动位置。
- 浮动窗口大小固定，不可在浮动窗口内修改文件夹尺寸。文件夹尺寸只能通过主面板右键菜单修改（需先关闭浮动窗口）。
- 网格面板缩小时（窗口调整），已打开的浮动窗口应自动关闭。
- 快速连续点击多个文件夹时，前一个应先关闭再打开新的。
- 文件夹内所有条目被拖出后，文件夹自动删除（空文件夹不允许存在）。
- 文件夹不能嵌套（不能将文件夹拖入另一个文件夹）。
- 合并创建文件夹时如果两个条目相距很远，新文件夹的位置选择策略：取两个条目中位置靠前的那个的坐标。如果该位置被占据，找最近的空位。
- 浮动窗口内右键删除条目：条目原地动画消失，文件夹实时更新。删除最后一个条目时，文件夹动画淡出并从主面板移除。
- 条目从浮动窗口拖出到主面板时，自动排列到主面板第一个可用空位（不允许手动指定位置）。
- 浮动窗口内条目支持拖拽重排（行为与主面板一致）。
- Alt+拖拽在浮动窗口内的行为与主面板一致：两个内部条目合并创建新文件夹放主面板（因为禁止文件夹嵌套）。
- 文件夹容量无硬性上限。网格模式折叠态溢出网格最多显示 4 个缩小条目；list 模式折叠态不截断，全部显示（可滚动）。
- list 模式折叠态的文件夹右下角预留一小块交互区域，点击该区域打开浮动窗口。
- 移动端触摸交互与桌面端拖拽行为的一致性（后续迭代处理）。

## Clarifications

### Session 2026-05-22

- Q: 文件夹展开时的最大尺寸是多少？ → A: 文件夹有一个统一最大尺寸，折叠态和浮动窗口共用，超出后浮动窗口内加滚动条。
- Q: 文件夹的展开方式？ → A: 打开浮动窗口，位置固定，覆盖在桌面上方，不推动相邻元素。
- Q: 文件夹展示模式（list/网格）的作用范围？ → A: 展示模式同时影响折叠态和展开态（浮动窗口）。
- Q: 条目移出文件夹后放到主面板什么位置？ → A: 自动排列到主面板第一个可用空位，不允许手动指定位置。
- Q: 合并创建文件夹的尺寸？ → A: 新文件夹 1×1，位于两个条目中位置靠前的那个的坐标。
- Q: 展开后文件夹内条目能否内部重排？ → A: 可以，支持拖拽重排，行为与主面板一致。
- Q: 展开后文件夹自身能否右键？ → A: 可以，浮动窗口标题栏右键提供与折叠态一致的菜单。
- Q: 主面板条目拖入浮动窗口后放哪？ → A: 窗口内部网格第一个空位。
- Q: Alt+拖拽文件夹内条目到同文件夹另一条目？ → A: 行为与主面板一致，合并创建新文件夹放主面板（禁止嵌套）。
- Q: 文件夹容量上限？ → A: 无硬性上限，折叠态溢出网格最多 4 个，浮动窗口内显示全部（带滚动条）。
- Q: 展开状态删除条目？ → A: 条目原地动画消失，文件夹实时更新。删到最后一个条目时文件夹动画淡出并移除。
- Q: 展开状态改文件夹大小？ → A: 不允许在浮动窗口内改大小。文件夹尺寸只能通过主面板右键菜单修改（需先关闭浮动窗口）。浮动窗口大小固定。

### Session 2026-05-22 (边界条件补充)

- Q: 浮动窗口位置具体在哪里？ → A: 文件夹卡片附近。遇到面板左边界或右边界时自动靠拢调整，不超出面板边界。
- Q: 浮动窗口打开期间主面板能否交互？ → A: 完全阻塞。用户点击窗口外部区域即关闭浮动窗口，关闭后主面板恢复交互。
- Q: 折叠态 list 模式可见条目数量？ → A: 不截断，全部显示，超出时可滚动。文件夹右下角预留一小块交互区域用于点击打开浮动窗口。
- Q: 浮动窗口是否可被用户拖动？ → A: 不可拖动，位置由系统决定。
- Q: 浮动窗口打开期间修改文件夹属性？ → A: 不允许在浮动窗口内修改文件夹尺寸。浮动窗口大小固定。尺寸修改只能通过主面板右键菜单（需先关闭浮动窗口）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 所有主面板元素（网页条目和文件夹）必须使用统一的网格组件系统，占据 m×n 个网格单元格。
- **FR-002**: 网页条目在任何位置（主面板、文件夹折叠态、文件夹浮动窗口内）必须使用相同的组件渲染，具有完全一致的外观和交互行为。
- **FR-003**: 文件夹必须以浮动窗口方式展开。窗口出现在文件夹卡片附近，遇到面板左/右边界时自动靠拢。窗口不可被用户拖动移动，不得推动或挤开任何相邻元素。
- **FR-004**: 文件夹浮动窗口打开和关闭应有平滑动画，在 300ms 内完成。
- **FR-005**: 当文件夹内条目数量未超出文件夹容量上限时，文件夹不可打开（所有条目已正常显示）。
- **FR-006**: 拖拽逻辑必须全域统一：主面板、文件夹折叠态、文件夹浮动窗口内的条目使用同一套拖拽系统。
- **FR-007**: 用户可以将条目从浮动窗口拖到窗口边框外部并松手，条目以 1×1 卡片形式自动排列到主面板第一个空位（不允许手动指定位置）。
- **FR-008**: 浮动窗口打开期间，主面板完全阻塞，用户不可操作主面板上的任何元素。点击浮动窗口外部区域即关闭窗口。
- **FR-009**: 合并创建文件夹时（Alt+拖拽），新文件夹必须直接在两个原始条目的位置原地生成，不得先出现在第一行再移动。
- **FR-010**: 组件改变大小时以左上角为锚点原地扩展：右侧有其他组件则推移它们；右侧为面板边界则组件自身移到下一行。
- **FR-011**: 文件夹折叠态中未被缩小的条目可以直接点击打开网页，也可以直接拖动。
- **FR-012**: 被缩小到溢出网格中的条目不可点击、不可拖动。
- **FR-013**: 所有位置的条目右键菜单必须完全一致。
- **FR-014**: 禁止文件夹嵌套。
- **FR-015**: 文件夹内最后一个条目被移出时，文件夹必须自动删除。
- **FR-016**: 浮动窗口打开后，用户点击窗口外部区域或按 Esc 键时，窗口关闭。
- **FR-017**: 浮动窗口内条目使用网格布局排列，与主面板布局一致。
- **FR-018**: 浮动窗口内条目支持拖拽重排，行为与主面板一致。
- **FR-019**: 浮动窗口标题栏右键提供上下文菜单（重命名、删除）。文件夹尺寸修改只能通过主面板右键菜单操作。
- **FR-020**: 条目从文件夹拖出到主面板后，自动排列到主面板网格第一个可用空位。
- **FR-021**: 主面板上的条目通过右键菜单"移动到文件夹"功能移入目标文件夹（浮动窗口打开期间主面板阻塞，需先关闭窗口）。
- **FR-022**: 合并创建的文件夹大小为 1×1，位于两个原始条目中位置靠前的那个的坐标。
- **FR-023**: 浮动窗口内删除条目时，条目原地动画消失，文件夹实时更新。删除最后一个条目时文件夹动画淡出并移除。
- **FR-024**: 浮动窗口大小固定，不可在窗口内修改。文件夹尺寸只能通过主面板右键菜单修改（需先关闭浮动窗口）。
- **FR-025**: 浮动窗口不超出面板边界。出现位置在文件夹卡片附近，遇到边界时自动靠拢调整。
- **FR-026**: 文件夹展示模式（list 或 1×1 网格）同时影响折叠态和浮动窗口内的显示。
- **FR-027**: 文件夹有一个统一的最大尺寸，不论展示模式为 list 或网格，折叠态和浮动窗口共用此最大尺寸。
- **FR-028**: 当文件夹内条目超出最大尺寸可容纳范围时，浮动窗口内显示滚动条，用户可滚动查看和拖动所有条目。
- **FR-029**: 网格模式折叠态溢出网格最多显示 4 个缩小条目；list 模式折叠态不截断，全部显示（可滚动）。
- **FR-030**: list 模式折叠态的文件夹右下角预留一小块交互区域，点击该区域打开浮动窗口。

### Key Entities

- **网格组件（GridComponent）**: 统一的网格单元，可以是网页条目或文件夹。所有组件共享相同的大小表示（m×n）、外观渲染和交互行为。
- **文件夹容器（FolderContainer）**: 一种特殊的网格组件，内部包含子组件。折叠态按展示模式显示子组件预览，点击后以浮动窗口方式展开显示所有子组件。
- **浮动窗口（FloatingWindow）**: 文件夹展开时的容器，出现在文件夹卡片附近（不可拖动移动），覆盖在桌面上方。打开期间主面板完全阻塞。内部使用与主面板一致的布局和拖拽系统，超出最大尺寸时显示滚动条。窗口大小固定，不可在窗口内修改。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 网页条目在主面板、文件夹折叠态、文件夹浮动窗口三个位置的外观完全一致（图标大小、间距、字体、颜色无差异）。
- **SC-002**: 文件夹浮动窗口打开动画在 300ms 内完成，不造成页面其他元素的任何位移。
- **SC-003**: 从浮动窗口拖拽条目到窗口外部松手时，操作成功率 100%（不出现条目丢失或无法放置的情况）。
- **SC-004**: 合并创建文件夹时，用户不会看到新文件夹先出现在第一行再跳转的情况。
- **SC-005**: 组件大小变更后，左上角位置保持不变（偏差为 0 像素）。
- **SC-006**: 展示模式切换后，折叠态和浮动窗口均立即更新为对应模式，无延迟或不一致。

## Assumptions

- 文件夹浮动窗口使用固定定位（fixed/absolute positioning），不影响 DOM 中其他元素的位置。
- 统一的拖拽系统需要将拖拽上下文提升到更高的组件层级，或将文件夹浮动窗口保留在拖拽上下文的 DOM 树内（而非使用 createPortal 跳出）。
- 现有的 `useGridLayout` hook 需要重构或替换，以支持碰撞推移逻辑而非仅碰撞下移。
- 合并创建文件夹的后端流程可能需要改为：先计算目标位置 → 创建文件夹 → 直接设置 gridX/gridY → 再移入两个条目，避免位置跳转。
- 浮动窗口的尺寸计算基于文件夹最大尺寸设置和视口限制。
- 条目移出文件夹到主面板时，使用自动排列算法（第一个可用空位），不支持手动指定放置位置。

## Architecture Analysis

### 当前架构为什么无法满足需求

1. **文件夹弹窗使用 createPortal 脱离 DndContext DOM 树**：
   - 解决方向：将文件夹浮动窗口保留在 DndContext DOM 树内，或使用单一 DndContext 包裹整个页面。

2. **弹窗内条目与主面板使用不同组件渲染**：
   - 解决方向：统一使用同一个 WidgetComponent 基础组件，根据上下文调整布局参数，保持交互逻辑不变。

3. **buildLayout 只有碰撞下移，没有碰撞右推**：
   - 解决方向：实现"锚定左上角 + 右推移"的碰撞策略。

4. **合并创建文件夹是"先创建 → 后移动"两步操作，中间有数据不一致**：
   - 解决方向：后端提供"原子合并"API，一步完成创建+定位+移入。

### 推荐的架构方向

- 文件夹浮动窗口保留在 DndContext DOM 树内（避免 createPortal），确保所有拖拽在同一上下文中
- 统一的 WidgetComponent 基础组件，根据上下文（主面板/文件夹内）调整布局参数，但保持交互逻辑不变
- 浮动窗口使用 CSS absolute/fixed 定位覆盖在桌面上方，不修改 DOM 中其他元素的位置
- 展示模式作为文件夹属性存储，渲染时根据模式选择 list 或网格布局
